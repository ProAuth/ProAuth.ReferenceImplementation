# Optional native purchasing-approvers group

The baseline uses direct assignment. This profile adds **one** authority for group eligibility: trusted provisioning from the Manufacturing native UserStore. It does not request group claims, enable SCIM, or query the directory during an API request. The [two-column decision trace](authorization.md) shows exactly where the extra condition applies.

The local Manufacturing UserStore and Procurement exercised this profile on 7 November 2026. Amir approved an independent purchase while eligible. After native group removal and a provisioning refresh, Procurement denied his same access token. [Live run and timing](#live-manufacturing-check)

## What ProAuth supplies

The product release identified in [product-build.json](../config/product-build.json) supports `userstore.proauth.net/v2` **Group**, `metadata.userStoreId`, and direct `relationships.memberUsers`. Native user and group IDs are GUIDs in that UserStore’s namespace. These are not OIDC subjects or the synchronized ProAuthGroup IDs. ProAuth also supports nesting. This reader checks **direct** members of the one mapped native group; it never follows parent/member groups, searches by display name or scans all groups.

The standard reference uses Enterprise custom claim rules for trusted issuer context. This profile reads direct group membership through the native UserStore v2 administration API. The provisioning identity needs scoped read permission on the Manufacturing UserStore.

## Provisioning contract

1. Verify the Manufacturing provider is attached to the intended Workforce tenant in the dedicated subscription, and verify Amir’s native fixture ID against the administrator’s account record. Separately verify his API issuer, subject and tenant as in [membership setup](running.md#business-membership-and-the-first-journey). Bind those identities to the same immutable purchasing person ID, `amir`. Recheck this binding after any identity migration. The purchasing operator alone assigns his local approver role, buyer, cost centre and CHF ceiling.
2. In a disposable environment, the identity administrator may import only the [owned native group](../config/proauth/optional-groups/45-approvers.yml) with `node scripts/mervikon.mjs provision-approver-group --env-file /private/path/mervikon.env`. The default manifests exclude it. This is **initial setup**: `memberUsers: mode: set` sets the direct membership of this dedicated group to Amir. Do not continually reimport it after an administrator removes him. Only the identity administrator changes group membership.
3. Register a separate confidential DPoP client for the operator-side job, authorized for `ProAuthManagementService` and **ProAuthGroup.Read** on only the Manufacturing UserStore. Use its own key and secret; do not use bootstrap, root, an application session or the Treasury workload. Require the canonical issuer’s HTTPS origin, the pinned Workforce tenant, and a trusted CA. Run [Group.Provisioner](../src/clients/Group.Provisioner/Program.cs) as a **single writer** with a directory dedicated to its output. Its environment uses the product `Authentication__Authority`, `Authentication__TenantId`, `Authentication__ClientId`, `Authentication__ClientSecret`, `Authentication__ClientAuthenticationMethod=ClientSecretBasic`, `Authentication__SenderConstrainedTokenMode=Dpop`, `Authentication__Dpop__JsonWebKey` and `GroupEligibilityDir` settings. Supply private values through the operator’s private environment, not command arguments or the APIs.
4. The job makes one authenticated TLS GET to `/api/userstore/v2/{manufacturingStoreId}/administration/Group/{purchasingGroupId}`. The [projection](../src/clients/Group.Provisioner/DirectGroup.cs) checks the returned group and store IDs and the store of each direct member. Only the owned Amir native user ID maps to `amir`. Wrong source/group, malformed or ambiguous data, transport failure or an oversize response withdraws the projection. The example caps the response at 256 KiB, 12 JSON levels and 64 direct members. These are application bounds, **not product directory limits**. Only issuer, tenant, one eligible person ID (or null) and read timestamp leave the job. No raw directory response, credential or proof belongs in logs.
5. Use separate Unix identities/ACLs in deployment: the provisioner may write only its eligibility directory, never the purchasing assignment directory. Keep each parent private and its dedicated child readable/traversable by the APIs. Set `GROUP_ELIGIBILITY_DIR` to the output directory. Select the [group overlay](../deploy/compose/group-approvals.yml) on **both** Procurement and Fulfilment with `node scripts/mervikon.mjs compose --group-approvals --env-file /private/path/mervikon.env -- up -d procurement-api fulfilment-api` at initial startup. Switching profiles recreates processes and clears demo state. Keep that overlay on subsequent recreations. Missing/malformed eligibility in this mode removes approver authority without falling back to direct approval.
6. Run `dotnet run --project src/clients/Group.Provisioner -c Release --no-build` once per refresh (for example, every 20 seconds, **no overlapping runs**). Synchronize host clocks. The read deadline is 15 seconds; an affirmative snapshot expires 60 seconds from **start of read**, not from publication. No automatic background job is installed by the reference.

## Removal with an already issued token

Until the next fresh source read and replacement, an otherwise eligible holder of an old token may still approve. Once the “not eligible” replacement is visible, the very same token cannot approve. A stopped job cannot extend a snapshot; at age **60 seconds** (or a future timestamp), it grants no eligibility. A failed read deletes the output; if publication/deletion or mount propagation fails, the age check is independent of the writer. In one HTTP test with the native DTO response fixture, refresh through atomic publication to the first denied response took 0.83 ms on the local filesystem. The same token had succeeded immediately before refresh. This measures application propagation only. The 60-second bound assumes the directory read itself reflects removal and clocks agree. A positive read already in flight can still publish its observation; in-flight API decisions and replica propagation have the same limits as [local assignment updates](authorization.md#assignments-and-updates). Removing the local approver role is an independent urgent withdrawal.

## Live Manufacturing check

On 7 November 2026, an operator harness signed Amir in through the registered Workplace authorization-code flow with PAR, PKCE and DPoP. A disposable Procurement instance validated the API token. The harness verified its subject against the issuer’s link for the Manufacturing provider and native Amir user ID before assigning the stable purchasing person ID. It kept one access token in memory for all three approval requests and sent a fresh proof with each one.

The test created the owned group through the native v2 API and added Amir as a direct member. A temporary confidential client had only `ProAuthGroup.Read` on the Manufacturing UserStore. It used the product client and [provisioning writer](../src/clients/Group.Provisioner/PublishEligibility.cs) to refresh the eligibility file. Three independent CHF 1,000 purchases requested by Elena started at revision 1. Each approval went through the normal Procurement HTTP endpoint.

| Time from native removal acknowledgement | Observed result |
|---|---|
| Before removal | With positive eligibility, Amir approved the first purchase. HTTP 200, Approved at revision 2. |
| 12.2 ms | A fresh native UserStore read confirmed that Amir was absent. |
| 14.6 ms | With the previous eligibility file still in place, the same token approved the second purchase. HTTP 200. |
| 36.1 ms | The scoped reader completed its native read and atomically published the withdrawal. |
| 42.2 ms | The same token received HTTP 403 with `approver_required` on the third purchase. It remained Requested at revision 1. |

The clock started when the native relationship DELETE returned successfully. These are elapsed times from one run with an immediate refresh and one API instance. For a periodically scheduled reader, add the wait for its next run and the time for its output to reach each API mount.

The group was absent before setup. Cleanup removed the group, reader registration, permission attachment, assignment and temporary role. Independent readback returned 404 for both the native group and its synchronized counterpart and found zero temporary reader registrations or roles.

To repeat the check, prepare three independent under-threshold purchases, keep the original token and sign each POST with its holder’s key. Use a separate pending purchase for the approval between removal and refresh. That keeps the final denial distinguishable from a revision conflict. The HTTP suite also covers urgent withdrawal of the application role while a positive directory observation is still current. [HTTP controls](../tests/Authorization.Http.Tests/GroupApprovalTests.cs) and [native source-ID controls](../tests/Workflow.Domain.Tests/DirectGroupTests.cs).
